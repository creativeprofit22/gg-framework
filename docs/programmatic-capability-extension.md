# Extending programmatic capabilities

[Workflow index](programmatic-workflow.md) · [Recommendation policy](programmatic-recommendation-policy.md) · [Architecture](programmatic-architecture.md)

## Extension contracts and reviewed command creation

Reviewed project-command creation is a separate normal follow-up through `programmatic_command`. Deterministic scanners retain their original three specialist routes. A separate reviewed `run` action accepts existing prompt commands through the same isolated session implementation; it requires neither creation nor an Opportunity. Creation reuses ordinary Markdown, the human-question bridge and normal tool/session history; it adds no persistent command registry, runner, dependency or dashboard.

## Unfamiliar-stack walkthrough

Consider a manifest-free operations directory with an extensionless runbook, a Python reconciliation module and synthetic CSV inputs/expected outputs. The same approach applies to an unfamiliar language or mixed monorepo:

1. **Find the workflow, not a framework label.** Read the runbook, relevant source and representative data under the existing bounded, permission-checked [evidence rules](programmatic-evidence.md#initial-sample-delivered-receipt-strict-inventory). Attribute each input/output to the correct subproject. Treat scripts as text, never execute/import them during discovery. An initial excerpt is orientation, not a delivered receipt; request actual allowed reads for supported claims. State ignored, unreadable and budget-limited areas.
2. **Describe the need before matching.** Identify the operator trigger, representative discrepancy, current process, desired report, success check and mutation boundary. Label repeatability as observed or inferred; an assumed frequency or missing expected output warrants more evidence. If it is a one-off correction, keep it manual.
3. **Inspect existing capability metadata, then exact bodies.** Use current discovery and `command_information`, preserving command owner/identity. Read plausible command bodies and local prerequisite evidence. A similarly named command is not a match. Compare inputs, output, side effects and verification: reuse an exact fit, propose an extension for a coherent partial fit, and avoid forcing unrelated retention work into reconciliation. Command definitions do not replace independent workflow evidence.
4. **Choose the smallest honest extension.** If existing read/navigation tools suffice, propose an ordinary prompt-only command. If deterministic transformation genuinely needs helper code, declare reviewed helper inputs/outputs, runtime/packages, normal/error/incomplete cases and unchanged-file assertions. The initial helper creation runtime is host Node, not a promise to create working Python/Rust helpers. An existing Python project can still receive read-only prompt advice; unestablished runtimes/prerequisites must remain explicit. Missing native UI, app APIs or tool functionality is application development, not a Markdown command that magically supplies it.
5. **Inspect, create, verify and run separately.** Follow the exact host workflow below in a normal authorized turn; a candidate review does not create files. An existing-command extension needs a later authorized ordinary edit/review because create-only publication cannot update it. Loading inspection is not behavioral proof. Test execution and reviewed command execution each require their own permission.
6. **Extend evidence/fixtures before central matching.** Add representative unfamiliar source, data and workflow cases to the existing evidence/connected fixture owners; do not add a language whitelist or central detector registry merely to make advice discover the stack. Deterministic scanners are a separate opt-in declarative profile/route contract, not model-generated repository scripts. Consult the existing test entry points below without expanding the fixed routes.

This is an authoring walkthrough, not a report that these illustrative files or a live model were run.

## Identity and review contracts

Exact command token, source and invocation kind are metadata, not shell text. Names preserve case, underscores, dots and hyphens (`check_project`, `CheckProject`, `check.project`); never trim, lowercase or rename references. The reference-only subset is 1–100 ASCII characters, beginning with a letter/digit and followed only by letters, digits, `.`, `_`, `-`. Leading punctuation, non-ASCII and other punctuation are excluded even if the slash parser accepts them. Slash prefixes/path separators, whitespace, controls and interpreter-like text are rejected. This does not change the loader/parser, scanner/policy IDs or three-specialist allowlist.

Content snapshots bind SHA-256 of private resolved owner identity, body SHA-256 and up to 32 sorted unique repository-relative helper path/digest pairs. Script-backed snapshots require helpers; prompt-only snapshots reject them. Workspace actions are host-owned/app-backed and cannot execute through this review contract. Availability is separate from permission. Source/resolved-owner changes invalidate identity even with unchanged name/body; the resolver owns precedence/private identity.

Project-only ephemeral creation proposals bind desired outcome, capability kind, inputs/outputs, prerequisites, risks, verification expectations, exact command/helper digests, destinations and prior digests or explicit absence. Command destinations are Markdown directly under `.gg/commands`. Pure schemas write nothing; the host consumes review and publishes command-last. `bodySha256` hashes parsed prompt; `files[].proposedSha256` hashes raw UTF-8 including frontmatter. Both are bound. No-replace Markdown publication is the commit point, not global multi-file atomicity or universal power-loss recovery.

Verification records bind content snapshot, model/provider/environment, normal/incomplete/out-of-scope cases, evidence and limits. Loading, behavior and side effects are separate. Passed readiness requires deterministic loading and behavioral cases; scripts additionally need deterministic error/incomplete and side-effect coverage. Model judgments cannot replace assertions. Failed/unavailable records remain representable; parsing does not execute or certify evidence claims.

Execution review separately binds purpose/proposal, source/body/helpers, exact arguments, configuration fingerprint, success condition and host settings. Settings contain policy ID/revision, provider/model, positive bounded turns/deadline and a recognized capability profile—not API keys, arbitrary tools or MCP servers. Represented limits are ceilings, not changed runtime defaults. Research-read-only rejects script-backed execution; app-backed execution remains unsupported.

`isProgrammaticReviewCurrent` compares parsed reviewed/current data against a host-only pending proposal ID, expected creation/execution purpose and explicit accepted decision. Missing/denied decisions, wrong purpose/proposal and content/argument/configuration/settings changes fail closed. Parsing/matching are **not user approval**, single-use consumption or replay prevention. Never construct host context from model output. The callback owner must consume approval once and re-resolve current content before later dispatch. Prior verification does not approve creation or execution.

## Reviewed missing-command follow-up

This starts only after an explicit creation request in a normal turn, **not** inside temporary read-only advisory scope. No `/setup-commit` retrofit, scanner route, Opportunities Run button or specialist registry expansion is involved.

1. **Inspect alternatives and proposed files.** Load deferred `programmatic_command` and call `inspect` with the missing-capability requirement, safe lowercase/hyphen name, ordinary Markdown and any helper text. The first result is bounded catalog review. Select likely candidates through `candidates` for body inspection, then submit current inventory hash with reviewed disposition/rationale. A suitable existing prompt returns `reuse`; manual and app-development outcomes are explicit. Suitability is a reviewed claim, not proven by matching name/hash.
2. **Review the exact proposal.** A creation proposal returns one session handle and complete preview: destination paths, exact Markdown/helper strings, raw hashes, parsed prompt identity, prior absence, required tools, prerequisite evidence, risks and verification expectations. Normal Markdown must state inputs, outputs, required tools, limits and argument behavior. No new frontmatter language or `$ARGUMENTS` substitution.
3. **Ask separately to create.** `create` accepts only that handle. The normal desktop session asks through its question card, with exact content and an explicit warning that creation runs nothing and grants no tools. Model booleans, copied approval records and free-text substitutes cannot approve it. The handle is consumed before awaiting review; rejection, timeout, cancellation, supersession, conversation changes, disposal and restart do not preserve permission. The host rechecks project identity, inventory, prerequisites and bytes after the answer and before publication.
4. **Publish without replacing files.** The sole discoverable file is `.gg/commands/<name>.md`. Helpers live in private non-recursive `.gg/commands/.<name>-helpers/`. Existing files/helper sets conflict even if apparently generated. Complete synced helpers precede a complete non-`.md` temporary sibling; an atomic hard link publishes Markdown only while destination remains absent. Unsupported hard links return unavailable—no overwrite rename or direct-visible-write fallback. Lock cleanup is confined to a unique operation-owned directory because the shared lock helper can reclaim stale files.
5. **Inspect loading separately from behavior.** Creation reports `created`, `loads`, `behavior: not-tested`, `executionApproved: false` separately, plus a verification handle. The shared loader/discovery resolve the new command immediately, without packaging. `verification` rehashes command/frontmatter/helpers/prerequisites and checks owner, selected runtime environment and append-only arguments. Same-session recommendation data names those limits; no universal verified badge.
   Verification responses keep `loads` separate from `reviewedContent: current | unavailable`, receipt validity and optional model judgment. `loads: true` means actual discovery resolved the expected project owner in this inspection; `loads: false` means no command for that identity. Omit the field when loading is unknown (cancelled/unknown session state, owner mismatch or failure before discovery). `reviewedContent: current` requires all snapshot checks; `unavailable` means identity was not established, not that Markdown cannot load. Command/frontmatter/helper/prerequisite edits can therefore return `{status: "unavailable", loads: true, reviewedContent: "unavailable", behavior: "unavailable", executionApproved: false}`. Missing, forged, evicted, capped or stale receipts leave successfully checked snapshot/loader as `{status: "unavailable", loads: true, reviewedContent: "current", behavior: "unavailable", executionApproved: false}` when only receipt validation fails. Rejected evidence returns no report, receipts, recommendation or model judgment; evidence-size rejection preserves independent observations. These are session-local observations, not a badge or execution permission.
6. **Prepare evidence without running tests.** `prepare_verification` records exact foreground bash command, test-file digests and requested assertion cases. It runs nothing and approves no execution. Separately authorized normal file/bash tools may run the project's reviewed fixture tests. Guarded session lifecycle records up to 64 host-generated test-result receipts, distinct from advisory retrieval receipts. Subsequent `verification` accepts only receipt IDs observed in this session, never model-authored call IDs as proof.

Inspection limits: one pending proposal, one Markdown plus at most 32 helpers, 128,000 bytes per file, 512,000 private content bytes and 64,000-byte complete JSON review ceiling. Oversize reviews are rejected, not truncated into approval. Catalog inspection uses existing bounded discovery limits and fails closed on incomplete/unreadable enumeration, including hidden filename/frontmatter/alias/case collisions. Only regular bounded UTF-8 files are accepted; traversal, Windows device/ADS/trailing-dot paths, links and unsafe ancestors are refused. Initial helper runtime is installed host Node (`.js`, `.mjs`, `.cjs` plus text/JSON/Markdown data); other runtimes are explicitly unestablished. Declared installed packages require readable regular local manifests; linked package directories may be unavailable. No prerequisite is installed.

Before Markdown commit, interruption may leave private helpers/staging only. Caught failures remove only still-matching operation-owned files and empty owned directories; changed user content is retained with residual paths. Old crash leftovers are not blindly reclaimed. After commit, notification/subsequent-check failure must still report created files. These path checks do not provide kernel-level directory-handle confinement against a hostile same-user process replacing ancestors; fixtures are not an OS sandbox.

Project-bound verification receipts exclude **every** `bash` call with `persist: true`, including first calls/platform fallbacks. Persistent execution works normally, but diagnostics describe launch directory and host environment fingerprints do not attest reused-shell cwd/modified exports. Preparation/verification report this limitation. Use a separately approved nonpersistent foreground call (`persist` omitted/false) for a limited receipt. Printed cwd/environment output is not trusted provenance; broader support requires transport-owned cwd/environment attestation.

**Evidence limitations are deliberate.** Host-observed completion, exit code or printed “all tests passed” does not prove arbitrary requested assertions ran. Receipts bind invocation input, command/helper/test bytes, configured provider/model, selected environment, output identity/capping and available host execution diagnostics. Known wrong cwd, edits during/later than a test, wrong model/environment, duplicate calls, forged IDs, capped output and restarted state invalidate applicable evidence. Declared assertion coverage and optional model judgment stay labeled. Unlisted dependency source/environment inputs are not fully fingerprinted.

The tool deterministically establishes loading only. Without host-established assertion linkage, overall behavior remains `unavailable`, even for zero exit; no universal parser/grading platform is invented. Actual normal/incomplete/out-of-scope prompt wiring and helper normal/error/unchanged-file assertions are exercised by existing scripted-provider/Vitest/Node fixtures, not arbitrary live-model quality. Real-model or paid trials require separate authorization.

Creation is unavailable without human review (including ordinary headless/CLI hosts), under denied tool policies, without local filesystem support, or in plan mode. Persistent child workers do not receive the tool automatically. Read-only inspection/evidence grants no file/execution permission. Other sessions must re-inspect helper assumptions; script-backed advisory availability remains unsupported. Updates, overwrites and global promotion are outside this create-only workflow.

## Direct reviewed execution

In a normal desktop code turn, load `programmatic_command`, request `action: "run"` with strict `selection`: version 1, canonical `command` reference (name/source/invocation kind), exact appended `arguments`, `outcome`, `successCondition`, sorted project-relative `helpers` and `prerequisites`, sorted `requiredTools`, `mode` (`read-only` or `general-work`) and `containment: "agent-session"`. Discovery, creation and verification are not execution approval. Existing built-in, project/global prompts can be selected; workspace actions and ambiguous/changed owners are refused.

The host separately presents full command/file preview and effective tools for approval. Read-only runs have no shell, mutation, install, indexing, child-agent, MCP or unrestricted corpus tools. General-work requires fresh exact-action approval for shell/mutation tools. Only host-supported tools can be granted; frontmatter/declarations grant no capabilities. Chat, plan, advisory, restricted child, remote-filesystem and unsupported/headless hosts cannot execute this action. The child cannot recursively call `programmatic_command`.

Raw content, parsed prompt, canonical owners, declared file contents/identities, arguments, outcome, success condition, effective tool policy, provider/model and runtime are fingerprinted. GG rechecks after review and around guarded dispatch, action approval and result acceptance. Changed content/permissions invalidate review rather than substituting new content. File reviews are bounded to 128 KB per file, 32 helpers, 512 KB aggregate and a 64 KB full preview; over-budget executable content is rejected, not truncated. Outside-project helpers are unsupported: bring a reviewed copy into the project or use a separately approved ordinary workflow.

**This is not an OS or filesystem sandbox.** Shell actions may reach outside the project. Declarations identify reviewed files, not every executable dependency. Checks cannot atomically prevent a hostile same-user process racing the final check and shell file open. Requests requiring OS confinement are refused. Preflight never installs/imports prerequisites.

Direct runs share repository claim, one transient session, cancellation, turn/deadline/evidence limits and cleanup. They write no synthetic Opportunity record and receive no parent conversation. Bounded results carry host run ID, execution/file/policy fingerprints and tool argument/result digests, but no child transcript. `completed` means finished with attributed tool evidence; `behavior: "unverified"` does not certify the success condition. Model judgment, opaque stdout and exit zero are not independent behavioral proof. Cleanup survivors retain ownership and cannot report success.

## Compatibility obligations

The authoritative boundaries are [setup-first slash discovery and code/plan modes](programmatic-user-flow.md#commands-and-ownership), [fixed scanner routing and retained states](programmatic-architecture.md), [history consent/compatibility](programmatic-recommendation-lifecycle.md), and the separate approval/confinement contracts above. Do not generate a duplicate project entry command, broadly rewrite existing profiles, auto-refresh setup from focus/research/ranking/catalog limits, or use a generic prompt fallback for unsupported execution. Advice omissions never mark scanner findings disappeared.
