## Assessment outcomes and evidence boundaries

Assessment status (`completed`, `incomplete`, `unavailable` or `cancelled`) is independent of scanner status. Setup always reports scanner `not-run`; configured results distinguish unavailable, denied, cancelled, failed and succeeded with host-owned enabled/applicable counts. A successful scan survives later provider failure/cancellation, including authoritative counts. A missing scan tool is a limitation, not an impossible advice prerequisite. Denied/cancelled work is not retried; cancellation stops assessment. Failed scans may accompany limited advice but never become successful scans. No fallback provider, installation or setup repair is attempted.

Unavailable credentials/provider can leave valid host-only facts and an exact reviewable proposal. Incomplete advice does not become completed just because settings are valid. Corrupt, unreadable or unsafe saved settings produce no replacement proposal or approval handle; safely collected evidence can still explain the limitation. Configured entry retains strict readiness/freshness gates, including inventory failure before provider entry. A completed empty recommendation list is not a universal clean bill of health.

### Initial sample, delivered receipt, strict inventory

Initial evidence is a stack-neutral sample, not strict inventory or delivered receipt proof: at most **200 overview paths**, **12 initial text excerpt attempts**, **16 KiB per excerpt**, and **64 KiB serialized aggregate evidence**, including escaping/UTF-8 accounting. The aggregate ceiling covers the evidence object, not all metadata or prompt framing. Extensionless and unfamiliar text participate without a framework allowlist. Root `.gitignore`, inventory exclusions, containment and safe regular-file reads apply; no project code is imported or executed. Traversal order bounds the path sample, followed by sorted excerpt selection—not a completeness/relevance guarantee.

The session supplies host authorization hooks for traversal (`find`) and each content read (`read`), **including `.gitignore`**, intersecting unavailable tools, disabled tools, capability grants, approval callbacks and execution validation. Live permission/cancellation checks recur after awaits and before delivery; denied material remains uninspected. An unreadable/unsafe/oversized ignore policy fails discovery closed rather than silently ignoring exclusions. These controls do not replace strict setup/profile policy.

Coverage distinguishes inspected, uninspected/budget-limited, unreadable/unsafe and nonmatching/not-applicable outcomes. Truncation and ordinary read/walk failures retain explicit diagnostics; counts describe observed omissions, not a complete census. Initial samples cannot substantiate an observed recommendation: accepted advice still requires actual delivered, post-cap host receipts and fresh exact candidate snapshots. Catalog coverage never establishes project coverage. Partial evidence never creates a configuration fingerprint, approval proposal or disappearance reconciliation; `buildProgrammaticInventory` retains strict failure behavior. Cancellation is cooperative, not a promise to interrupt an already pending filesystem system call.

## Bounded available-command advice and targeted research

`/programmatic [focus]` and **Check for opportunities** share `AgentSession.assessProgrammatic`, as do `/setup-programmatic` and **Review setup** in inspect-only mode. Host preinspection supplies exact setup facts or one permitted unchanged `programmatic_scan({})` before the provider turn; the model is told not to repeat either. **Recommendations — not started** remains ordinary transcript content. The desktop additionally renders typed candidate projections and history as described in [User flow](programmatic-user-flow.md#discover-and-review-candidates). Neither that projection nor its read-only review enters deterministic reconciliation or approves execution; there is no advisory Run button or automatic execution.

The host activates a temporary read-only scope from the resolved built-in command, not focus, Markdown or source text. It intersects existing grants, unavailable tools and approval callbacks. Configured assessment permits read/navigation, constrained web tools, `command_information`, the read-only `research_corpus` facade and result submission. Setup is narrower: contained read/navigation, command information, result submission and inspect-only profile access. Neither permits mutation, shell, orchestration, raw corpus indexing, MCP or authority-expanding discovery. The scan counter is claimed synchronously before awaiting execution. Cleanup runs in `finally`; incomplete/cancelled/provider-error assessments retain completed scans and receive an incomplete-advice notice. Subsequent normal turns recover only prior permissions.

Runtime ceilings: 10 catalog pages including initial page, 320,000 cumulative metadata characters, 12 candidate bodies, 64 session-only evidence receipts with oldest eviction, and one validated result under the [advisory result limits](programmatic-recommendation-policy.md#domain-representations-and-limits). [Per-page/body limits](programmatic-architecture.md#command-discovery-and-refresh) also apply. Submission rechecks inspected catalog pages and exact host-owned snapshots; partial/changed catalogs and unreadable candidates force limited coverage. Retrieval/identity checks do not establish semantic ranking quality or truth of model-authored claims.

`core/research-policy.ts` shares conditional local-first guidance across assessment, advice/manual work, command design, execution questions and review/maintenance. Detailed evidence guidance accompanies `tools/research-corpus.ts`. Search/discovery produce leads; relevant source inspection is needed for external attribution. Repository addition/installation is unavailable through the facade, including discover-with-add. Explicit general `/steroids` indexing is unchanged. No backend, dependency, index, cache or worker service was added.

Receipts retain a host ID, bounded tool-call ID, retrieval/lead/failure/cancellation distinction and available source identity/location, not source bodies. Local numbered reads can substantiate inspected line ranges. Corpus attribution uses repository URL plus inspected path, not a claim that the live GitHub URL was fetched. Explicit bounded response revision metadata may be retained; missing revisions/external line ranges are not invented. Web multi-URL/follow-only or non-text results without attributable identity remain provenance limitations rather than synthesized citations. Receipts are transient and cleared on disposal; normal transcript history remains session-owned.

Evidence uses observed/inferred/assumed meanings and bounded local locations, at most 50 items per recommendation. External attribution adds an inspected HTTP(S) URL, optional revision/location and supported claim. Credential-bearing URLs, query strings/fragments and invalid line ranges are rejected. No fetched/source-body fields or absolute local paths. Attribution is not proof, permission or a network request; hosts must not copy secrets into free text or URLs. [Durable history evidence](programmatic-recommendation-lifecycle.md#observations-evidence-and-coverage) owns persistence projection and exact external receipt matching, including the current absence of verified external receipt line ranges.

## Developer verification and exclusions

The following developer verification material is retained from the former combined workflow. It describes fixture scope and historical evidence, not fresh runs. [Evaluation](programmatic-evaluation.md) owns the current protocol and local commands; the [scoped handoff](../.gg/evidence/cross-project-discovery-verification.md) records observed results.

Owning tests are under `packages/ggcoder/src/core/programmatic`, with tool and desktop-adapter tests next to their implementations. The connected execution fixture uses real discovery/profile/lifecycle/dispatch operations, an explicitly substituted detector route, and a harmless scripted provider. Its fresh-module recovery test is not a full operating-system restart test.

The Windows developer smoke supports `--integrated-recovery` for one minimized setup→execution→drift/refresh→persisted-state-recovery scenario. It records ordered native-window samples and exact owned-process cleanup evidence. Samples are not continuous monitoring. The fixture uses an isolated home/project and scripted provider, not production credentials. `--drift-only` and explicit `--visual` retain separate scenarios; neither may be combined with integrated recovery. A normal-window fallback cannot satisfy minimized verification.

The same developer smoke also supports `--extended-workflow`: setup and a completed Opportunity precede focused advice, reviewed prompt-only creation, canonical loading inspection, separate direct-run approval, renderer catalog refresh, direct child isolation and renderer reload/rescan. It is separate from drift-only/integrated recovery. `--extended-workflow --visual` exercises native WebView typing and review-card layout at 600×640 and 480×640; the nonvisual run samples a minimized window and uses scripted DOM input. Native fixtures use an exact bounded scripted-provider sequence, not a live model. Helper behavioral cases belong to backend fixtures; loading-only native inspection is not behavioral certification. Session-only proposals and receipts are not durable lifecycle history or permission after restart.

The integrated verification excludes packaging, installer, updater, release and broad visual campaigns. Feature exclusions are owned by [Architecture](programmatic-architecture.md#exclusions).

Scripted-provider fixtures exercise a built-in outside the three-specialist runner, project custom advice, manual and missing-app choices, no recommendations, local-only versus search/show research, simultaneous scan requests, failure/cancellation, max-turn cleanup, disposal during read I/O, queued-message restrictions and normal-run permission restoration. They compare profile/lifecycle bytes with a scan-only baseline including completed and dismissed findings. Corpus transport/content in the research fixture are mocked; model recommendation quality, actual external-source quality and native display were not evaluated. The earlier advisory report recorded 530 passing tests at its own source snapshot; consult the current verification handoff for later retained failures, not that historical count. The stale bloat assertion now pins the existing shared contract explicitly and checks its dependency/I/O-free boundary; no new dependency was added. See the scoped verification handoff for source provenance, retained earlier failures and limits. This is not a release claim.
