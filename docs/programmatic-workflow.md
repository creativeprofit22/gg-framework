# Programmatic workflow

Programmatic setup starts with a bounded, read-only assessment of the project's needs and workflows, alongside exact host-generated scanner settings. It does not require a recognized framework, manifest or available specialist to offer useful advice, and never turns repository scripts or instructions into executable scanners. Start with `/setup-programmatic`, review the assessment and settings, and approve saving separately. Then `/programmatic` assesses needs using the current session and selected provider/model, with an independent deterministic scan of the approved profile. Neither advice, setup approval nor scanning starts or approves a specialist task.

Recommendation saving, exact matching, human-confirmed correspondence, consent/legacy upgrades, retention and recovery are documented in [Recommendation history lifecycle](programmatic-recommendation-lifecycle.md). That history is separate from the deterministic results described below; its host interfaces do not add candidate controls to Opportunities.

## Commands and ownership

Both commands are built-in, code-mode workflows. They are not general chat prompts or shell launchers. Discovery advertises `/setup-programmatic` first and withholds `/programmatic` until the saved setup is approved and current. Direct calls without current setup return setup or repair guidance rather than starting the model. `/programmatic-run` is an internal selection/approval path, not an advertised executable command.

`/programmatic` accepts optional advisory focus, for example `/programmatic check packaging risks`. Focus is trimmed, limited to 4,000 characters, and accepts multiline or non-ASCII text but not prohibited control characters or attachments. Empty focus requests a general assessment. Focus is carried to the model as untrusted advisory context: it does not filter the deterministic scan, change settings, select opportunities or approve execution.

The model receives a bounded command-metadata page rather than every command body. `command_information` can read further pages or one exact discovered prompt body. Metadata and bodies are information, not evidence of suitability or permission to execute. Workspace actions have no specialist prompt body, and unavailable, changed, unsafe or oversized bodies are refused. This context wiring is not a completed semantic recommendation engine and does not expand the fixed specialist registry below.

The desktop **Opportunities** view exposes the same bounded setup, report, scan, selection and approval operations. Non-code sessions cannot use this workflow; plan mode does not authorize writes or task execution.

The CLI/daemon package owns discovery, profile persistence, lifecycle storage, route resolution and isolated execution. Shared desktop wire contracts live in `gg-core`; the React view renders those contracts and sends actions through the native Tauri bridge. The webview does not receive daemon bootstrap credentials or call the daemon directly.

The fixed specialist registry permits only:

| Specialist | Required owner | Availability and authority |
| --- | --- | --- |
| `/setup-tauri-package` | Built-in | Bundled, for supported Tauri package structure; mutating actions require their own approvals. |
| `/research` | Global custom command | Machine-local, not guaranteed to exist elsewhere; physically read-only tool list. |
| `/setup-sweep` | Global custom command | Machine-local, not guaranteed to exist elsewhere; can mutate after separate approval. |

A name in a profile does not make that specialist available. GG checks the current owner, command body and route before execution and again after approval. Missing commands, project-level shadows, changed bodies and unsupported routes fail closed. The current deterministic detector recognizes Tauri packaging structure; the registry is not a promise of discovery for every possible research or sweep task.

## Command discovery and refresh

The catalog is derived from GG's existing definitions, Markdown loader and host-owned actions, not another store or parser. Readiness uses the existing profile assessment: fresh projects avoid inventory, concurrent session checks share work, and later requests recheck rather than caching readiness indefinitely. Look-ahead checks do not assemble model command context.

Advisory pages contain at most 100 entries and 32,000 UTF-16 code units including JSON, with explicit continuation and limited coverage. Oversized metadata is summarized without changing command identity. Body responses have the same text limit and refuse oversized bodies rather than returning partial executable templates. Cancellation returns an unavailable result. The existing loader still parses command bodies locally; this is not a new lazy filesystem index.

Desktop and terminal refresh when the command menu reopens. Desktop also refreshes on window focus and run completion, including cancellation/failure; ACP republishes after turns. Setup saves use existing lifecycle callbacks. Successful empty results clear stale entries; failed responses preserve the previous catalog. Old pane/client/mode/generation responses cannot replace the current desktop list. Historical invocations use complete definitions and omit appended advisory metadata from their displayed command text.

## Review, save, scan, select, approve

The model-facing setup tool also requires a separate host question before saving a session-owned inspected proposal. Approval is single-use and bound to the exact configuration, profile, prior-file digest, session and project; these are revalidated before commit. Cancellation, reset, replay and owner/configuration drift invalidate it. `/setup-programmatic` is capability-restricted to inspection for the entire initial invocation, even if the model ignores the prompt. Generation requires a later invocation and host review. Hosts without an appropriate question transport, including the terminal tool registry, return `unsupported-host` without saving. The native **Approve and save setup** workflow remains separate and unchanged. Neither setup route approves command execution.

1. **Review setup** uses the same current-session assessment owner as `/setup-programmatic`: bounded project/workflow evidence and command matching, plus a separately host-inspected exact declarative profile, fingerprint, routes, exclusions and configuration changes. Initial setup writes nothing, runs no scanner and dispatches no specialist. An empty scanner profile is valid: it means no enabled deterministic checks, not no useful work.
2. **Approve and save setup** saves the reviewed profile. A configuration fingerprint and prior-file digest guard against concurrent changes; neither digest is user approval. A stale proposal must be inspected and approved again.
3. **Check for opportunities** uses the same current-session assessment owner as `/programmatic [focus]`. Before provider entry, the host attempts exactly one unchanged `programmatic_scan({})` when permitted; the model must not repeat it. Needs assessment is independent of enabled scanner count or specialist availability. Only the deterministic scan reconciles scanner results; an unchanged scan leaves scanner lifecycle bytes unchanged. Advice does not start tasks.
4. Select one result to inspect its evidence, route, risks and success condition. Selection and **Refresh results** are reads, not execution permission. **Dismiss this item** records a snapshot-guarded soft dismissal.
5. **Review task approval** asks separately before an isolated specialist starts. It names whether the task is read-only or may mutate. A mutating specialist's scope is task context, not a filesystem sandbox: later tool actions and plans require their own approval.
6. Review the result and explicitly rescan when appropriate. Rescans retain terminal history and stable opportunity identity rather than rerunning completed work.

Execution uses a transient child session with the selected provider/model and necessary project context, not the parent's conversation. It does not persist a child transcript. Research lacks write, edit, shell, installation, corpus-addition and MCP capabilities. This restriction does not mean research has no network access: allowlisted read-only web/corpus tools may be available. Completion must match the selected success condition and cite observed successful tool calls; that is attributed specialist evidence, not independent host certification. Failure, cancellation, deadline and cleanup outcomes remain distinct.

## Needs-first advice

Both entry modes share one focused policy: describe inspected workflows before capability matching, independently of existing automation. Each recommendation states its trigger, representative case, inputs, current process, output, success check, affected subproject, mutation boundary and repeatability basis, alongside evidence and uncertainty. Observed recurrence is distinct from inferred repeatability; assumed needs cannot support a positive automation recommendation. Frequency and time savings must not be invented.

Choose **reuse unchanged**, **extend existing automation**, **new capability**, **manual work**, or **needs more evidence**. Positive choices explain at least one plausible alternative; duplicate proposals should be consolidated. A covered need can yield one reuse recommendation while a different need justifies a new capability. Partial catalog coverage limits absence claims, not which needs may be discovered; empty advice remains valid.

Reuse, extension bases and concrete available-command alternatives require delivered snapshots and inspected local prerequisite evidence. All positive choices, including new capabilities, require independent local workflow support. Command-definition files retrieved through `read` or `code_search` remain capability evidence, but cannot supply that independent support: the host classifies locations against current discovered command owners and canonical file identities, not Markdown content or model labels. Mixed search receipts qualify only through inspected non-command local locations, honoring the cited location when supplied. Unclassified locations do not establish independence; ordinary Markdown workflow documents remain eligible. The model explains relevance; host receipt checks prove provenance, not semantic suitability or working prerequisites. An unresolved extension base requires more evidence. A previously inspected base or alternative that changes before submission remains visibly unavailable, with limited coverage.

Extensions are **proposals only**, requiring a later explicitly authorized edit/review—not an overwrite/update action on `programmatic_command`. New supported commands retain the separate inspect/create/verify/reviewed-run path. Missing app/native/tool functionality remains development work, never a generated working command.

## Assessment outcomes and evidence boundaries

Assessment status (`completed`, `incomplete`, `unavailable` or `cancelled`) is independent of scanner status. Setup always reports scanner `not-run`; configured results distinguish unavailable, denied, cancelled, failed and succeeded with host-owned enabled/applicable counts. A successful scan survives later provider failure or cancellation, including its authoritative counts. A missing scan tool is a limitation, not an impossible advice prerequisite. Denied/cancelled work is not retried; cancellation stops assessment. Failed scans may accompany limited advice but never become successful scans. No fallback provider, installation or setup repair is attempted.

Unavailable credentials/provider can leave valid host-only facts and an exact reviewable proposal. Incomplete advice does not become completed just because settings are valid. Corrupt, unreadable or unsafe saved settings produce no replacement proposal or approval handle; safely collected evidence can still explain the limitation. Configured entry retains strict readiness/freshness gates, including inventory failure before provider entry. A completed empty recommendation list is not a universal clean bill of health.

Initial evidence is a stack-neutral sample, not strict inventory or delivered receipt proof: at most **200 overview paths**, **12 initial text excerpt attempts**, **16 KiB per excerpt**, and **64 KiB serialized aggregate evidence**, including escaping/UTF-8 accounting. The aggregate ceiling covers the evidence object, not all command metadata or prompt framing. Extensionless and unfamiliar text participate without a framework allowlist. Root `.gitignore`, inventory exclusions, containment and safe regular-file reads apply; no project code is imported or executed. Traversal order bounds the path sample, followed by sorted excerpt selection—not a completeness or relevance guarantee.

The session supplies host authorization hooks for traversal (`find`) and each content read (`read`), **including `.gitignore`**, intersecting unavailable tools, disabled tools, capability grants, approval callbacks and execution validation. Live permission/cancellation checks recur after awaits and before delivery; denied material remains uninspected. An unreadable/unsafe/oversized ignore policy fails discovery closed rather than silently ignoring exclusions. These controls do not replace the existing strict setup/profile policy.

Coverage distinguishes inspected, uninspected/budget-limited, unreadable/unsafe and nonmatching/not-applicable outcomes. Truncation and ordinary read/walk failures retain explicit diagnostics; counts describe observed omissions, not a complete census. Initial samples cannot substantiate an observed recommendation: accepted advice still requires actual delivered, post-cap host receipts and fresh exact candidate snapshots. Catalog coverage never establishes project coverage. Partial evidence never creates a configuration fingerprint, approval proposal or disappearance reconciliation; `buildProgrammaticInventory` retains its strict failure behavior. Cancellation is cooperative, not a promise to interrupt an already pending filesystem system call.

## Files and lifecycle meanings

The programmatic workflow owns these fixed project-relative files:

- `.gg/programmatic/profile.json`: versioned approved declarative scanner profile and configuration baseline. It contains no executable scanner bodies or arbitrary command lines.
- `.gg/programmatic/state.json`: current bounded opportunity and lifecycle records.
- `.gg/programmatic/state.previous.json`: the previous validated lifecycle snapshot, when available. It is not an off-machine backup or a guarantee against disk loss.

Writes use validated, guarded temporary-file replacement and serialization. Temporary/lock artifacts are implementation details, not additional user-configurable routes. A specialist can create its own separately approved outputs; these are not automatic setup outputs.

| State | Meaning |
| --- | --- |
| `discovered` | Observed opportunity, not permission to run it. |
| `queued` | Accepted lifecycle transition toward execution; not a background scheduler. |
| `running` | An execution owns the record. Conflicting actions are unavailable until valid settlement. |
| `completed` | Execution completion was accepted after its evidence and cleanup checks. Rescan preserves this history. |
| `dismissed` | Soft-dismissed by the user; retained during reconciliation. |

Report status is separate from a record's state. A report can be stale or recovered while still showing a completed or dismissed record. A disappearing terminal opportunity remains in history. Failures are not silently promoted to completed.

## Configuration drift and legacy setup

GG compares the saved configuration baseline with current configuration inputs and policy. Manifest/configuration changes can require setup refresh; ordinary source or lifecycle changes do not by themselves require a new profile.

When configuration drifts, inspection shows exact added, removed and modified inputs and policy/schema/exclusion changes. Old results remain inspectable, but task execution and scanning are blocked until required setup approval is current. **Review setup refresh** does not write. **Approve and save refresh** changes the profile only; it does not scan or reset lifecycle records. A subsequent **Check for opportunities** reconciles the new configuration while preserving identity and terminal history.

A current setup needs no regeneration. A supported legacy profile can require explicit upgrade approval. Legacy data without a per-file baseline cannot explain historical file-level differences: GG reports that limitation rather than inventing changes. Unreadable or unsupported setup is not permission to overwrite it.

## Recovery and interrupted ownership

Use **Refresh results** (or **Retry loading results** after an error) to inspect saved data without repairing it. If the primary lifecycle file is invalid and a previous validated snapshot exists, the report can show older saved results. Reads preserve both files byte-for-byte. **Check for opportunities** explicitly reconciles and writes a valid primary when the current profile and ownership checks permit it; invalid primary bytes must not replace the valid previous snapshot.

If no validated state is available, stop and preserve the files and diagnostics. There is no automatic destructive reset or guarantee that lost history can be reconstructed. Do not delete lifecycle files to clear a warning.

Reloading the application or a module does not prove an interrupted specialist has stopped. Persisted active ownership continues to block conflicting actions. GG does not silently clear a running owner on restart, and the inspection/recovery controls are not a force-unlock API. Preserve diagnostic evidence for investigation when ownership cannot be settled normally. Recovery from corrupt lifecycle state is distinct from daemon restart or Roadmap notification recovery.

## Developer verification and exclusions

Owning tests are under `packages/ggcoder/src/core/programmatic`, with tool and desktop-adapter tests next to their implementations. The connected execution fixture uses real discovery/profile/lifecycle/dispatch operations, an explicitly substituted detector route, and a harmless scripted provider. Its fresh-module recovery test is not a full operating-system restart test.

The Windows developer smoke supports `--integrated-recovery` for one minimized setup→execution→drift/refresh→persisted-state-recovery scenario. It records ordered native-window samples and exact owned-process cleanup evidence. Samples are not continuous monitoring. The fixture uses an isolated home/project and scripted provider, not production credentials. `--drift-only` and explicit `--visual` retain separate scenarios; neither may be combined with integrated recovery. A normal-window fallback cannot satisfy minimized verification.

The same developer smoke also supports `--extended-workflow`: setup and a completed Opportunity precede focused advice, reviewed prompt-only creation, canonical loading inspection, separate direct-run approval, renderer catalog refresh, direct child isolation and renderer reload/rescan. It is separate from drift-only/integrated recovery. `--extended-workflow --visual` exercises native WebView typing and review-card layout at 600×640 and 480×640; the nonvisual run samples a minimized window and uses scripted DOM input. Native fixtures use an exact bounded scripted-provider sequence, not a live model. Helper behavioral cases belong to backend fixtures; loading-only native inspection is not behavioral certification. Session-only proposals and receipts are not durable lifecycle history or permission after restart.

This feature does not include arbitrary shell scanning, model-generated scanners, generic specialist fallback, global availability guarantees, multi-opportunity concurrency, background scheduling, cloud sync, telemetry or dashboards. The integrated verification excludes packaging, installer, updater, release and broad visual campaigns. Programmatic lifecycle recovery is not a backup service.

## Extension contracts and reviewed command creation

Setup-first discovery, focus/context, bounded advice and command information are implemented as described above. Reviewed project-command creation is a separate normal follow-up through `programmatic_command`, described below. The deterministic scanner still routes only to its original three specialists. A separate reviewed `run` action now accepts existing prompt commands through that same isolated session implementation; it requires neither creation nor an Opportunity. The creation path reuses ordinary Markdown, the existing human-question bridge and normal tool/session history; it adds no persistent command registry, runner, dependency or dashboard.

### Direct reviewed execution

In a normal desktop code turn, load `programmatic_command` and request `action: "run"` with a strict `selection`: version 1, canonical `command` reference (name/source/invocation kind), exact appended `arguments`, `outcome`, `successCondition`, sorted project-relative `helpers` and `prerequisites`, sorted `requiredTools`, `mode` (`read-only` or `general-work`) and `containment: "agent-session"`. Discovery, creation and verification are not execution approval. Existing built-in, project and global prompts can be selected; workspace actions and ambiguous or changed owners are refused.

The host separately presents the full command/file preview and effective tools for approval. Read-only runs have no shell, mutation, install, indexing, child-agent, MCP or unrestricted corpus tools. General-work runs require a fresh exact-action approval for shell and mutation tools. Only host-supported tools can be granted; frontmatter and declarations cannot grant capabilities. Chat, plan, advisory, restricted child, remote-filesystem and unsupported/headless hosts cannot execute this action. The child cannot recursively call `programmatic_command`.

Raw command content, parsed prompt, canonical owners, declared file contents/identities, arguments, outcome, success condition, effective tool policy, provider/model and runtime are fingerprinted. GG rechecks after review and around guarded dispatch, action approval and result acceptance. Changed content or permissions invalidate the review rather than substituting new content. File reviews are bounded to 128 KB per file, 32 helpers, 512 KB aggregate and a 64 KB full preview; over-budget executable content is rejected, not truncated. Outside-project helper declarations are unsupported: bring a reviewed copy into the project or use a separately approved ordinary workflow.

**This is not an OS or filesystem sandbox.** Shell actions may reach outside the project. Declarations identify reviewed files, not every executable dependency. These checks cannot atomically prevent a hostile same-user process racing the final check and a shell's file open. Requests requiring OS confinement are refused. Preflight never installs or imports prerequisites.

Direct runs share the existing repository claim, one transient session, cancellation, turn/deadline/evidence limits and cleanup. They write no synthetic Opportunity record and receive no parent conversation. Bounded results carry a host run ID, execution/file/policy fingerprints and tool argument/result digests, but no child transcript. `completed` means the run finished with attributed tool evidence; `behavior: "unverified"` explicitly does not certify the success condition. Model judgment, opaque stdout and exit zero are not independent behavioral proof. Cleanup survivors retain ownership and cannot report success.

### Domain representations and limits

`contracts.ts` owns the extension records and pure validation. Active advisory results/recommendations use V2; legacy V1 exports and transcript text remain unchanged and are not silently enriched. Scanner lifecycle and creation contracts are unchanged. The separate history contracts, opt-in profile V3 and additive display-only history status are described in [Recommendation history lifecycle](programmatic-recommendation-lifecycle.md).

- **Assessment:** omitted focus means general assessment. The implemented advisory-context adapter trims input, omits empty focus and validates the assessment before supplying model context. Supplied focus must contain nonempty text, at most 4,000 characters, with no controls except normal whitespace. Focus does not change scanner configuration or identity.
- **Advice:** active V2 recommendations have `kind: advisory`, outcome, rationale, uncertainty, evidence, the required workflow and up to four distinct alternatives. The five-branch choice contains only its relevant fields; unknown authority/lifecycle fields are rejected. Positive automation requires a meaningful alternative and inspected local support. V2 results cap recommendations at 10 and serialized characters at 64,000 including host limitations; coverage is scoped complete or limited with a reason. Legacy V1 compatibility retains its old schema, not an active submission bypass. The actual Responses serializer retains its existing non-strict sampling fallback for nested choice schemas; strict host validation remains mandatory. No shared-provider change is made.
- **Evidence:** reuse observed/inferred/assumed meanings and bounded local locations. Up to 50 items per recommendation; external attribution adds an inspected HTTP(S) URL, optional revision/location and supported claim. Credential-bearing URLs, query strings/fragments and invalid line ranges are rejected. No fetched/source-body fields or absolute local paths. Attribution is not proof, permission or a network request; hosts must not copy secrets into free text or URLs.
- **Identity and availability:** the exact command token, source and invocation kind are metadata, not shell text. Reference names preserve case, underscores, dots and hyphens (for example, `check_project`, `CheckProject`, `check.project`); they are never trimmed, lowercased or renamed. The reference-only token subset is 1–100 ASCII characters, starting with a letter or digit and followed only by letters, digits, `.`, `_` or `-`. Deliberately excluded even if the existing slash parser accepts them: leading punctuation, non-ASCII names and other punctuation. Slash prefixes/path separators, whitespace, controls and interpreter-like text are rejected. These limits do not change the existing loader/parser, scanner or policy IDs, or the executable three-specialist allowlist. Content snapshots bind a SHA-256 of private resolved owner identity, body SHA-256 and up to 32 sorted unique repository-relative helper path/digest pairs. Script-backed snapshots require helpers; prompt-only snapshots reject them. Workspace actions are host-owned/app-backed and cannot be executed by the review contract. Available/unavailable is separate from permission. Source or resolved-owner changes invalidate identity even with an unchanged name/body; the resolver remains responsible for precedence and private owner identity.
- **Creation:** project-only ephemeral proposals bind desired outcome, capability kind, inputs/outputs, prerequisites, risks, verification expectations, exact command/helper digests, destinations, and prior digests or explicit absence. Command destinations must be Markdown files directly under the existing `.gg/commands` loader directory. The pure schema writes nothing: the separate host workflow below consumes review and publishes command-last. `bodySha256` hashes parsed prompt content; `files[].proposedSha256` hashes raw UTF-8 bytes, including frontmatter. The host binds both. The command commit point is no-replace publication, not a claim of global multi-file atomicity or universal power-loss recovery.
- **Verification:** records bind a content snapshot, model/provider/environment, normal/incomplete/out-of-scope cases, evidence and explicit limits. Loading, behavior and side effects are distinct categories. Passed readiness requires deterministic loading and behavioral cases; scripts additionally require deterministic error/incomplete and side-effect coverage. Model judgments cannot replace those assertions. Failed/unavailable records remain representable. Evidence claims are not independently executed or certified by parsing.
- **Execution review:** a separate purpose/proposal binds source/body/helpers, exact argument text, configuration fingerprint, success condition and host-selected settings. Settings contain policy ID/revision, provider/model, positive bounded turns/deadline and a recognized capability profile—not API keys, arbitrary tools or MCP servers. The represented limits are ceilings, not changed runtime defaults. Research-read-only rejects script-backed execution; app-backed execution remains unsupported.

`isProgrammaticReviewCurrent` compares parsed reviewed/current data against a host-only pending proposal ID, expected creation/execution purpose and an explicit accepted decision. Missing/denied decisions, wrong purpose/proposal and content/argument/configuration/settings changes fail closed. Parsing and matching are **not user approval**, single-use consumption or replay prevention. Never construct the host context from model output. The existing callback owner must consume approval once and re-resolve current content immediately before a later dispatch. Prior verification does not approve creation or execution.

### Bounded available-command advice and targeted research

`/programmatic [focus]` and **Check for opportunities** share `AgentSession.assessProgrammatic`, as do `/setup-programmatic` and **Review setup** in inspect-only mode. Host preinspection supplies exact setup facts, or one permitted unchanged `programmatic_scan({})`, before the provider turn; the model is told not to repeat either. **Recommendations — not started** belongs in the normal transcript. The card displays a bounded assessment summary and independent deterministic outcome through the existing native response. Advice never enters Opportunities, task selection, approvals or lifecycle reconciliation; there is no advisory Run button, new endpoint or automatic execution.

The host activates a temporary read-only scope from the resolved built-in command, not text in focus, Markdown or source. It intersects with existing tool grants, unavailable tools and approval callbacks. Configured assessment permits read/navigation, constrained web tools, `command_information`, the read-only `research_corpus` facade and result submission. Setup is narrower: contained read/navigation, command information, result submission and inspect-only profile access. Neither scope permits mutation, shell, orchestration, raw corpus indexing, MCP or authority-expanding discovery. The scan counter is claimed synchronously before awaiting execution. Scope cleanup runs in `finally`; incomplete/cancelled/provider-error assessments retain any completed scan and receive an incomplete-advice notice. Normal subsequent turns recover only their prior permissions.

Runtime ceilings remain: 10 catalog pages including the initial page, 320,000 cumulative metadata characters, 12 candidate bodies, 64 session-only evidence receipts with oldest eviction, and one validated result of at most 10 recommendations/64,000 serialized characters. Existing per-page/body limits remain. Submission rechecks inspected catalog pages and exact host-owned command snapshots; partial/changed catalogs and unreadable candidates force limited coverage. These checks establish retrieval and identity, not semantic ranking quality or the truth of model-authored claims.

### Reviewed missing-command follow-up

This workflow starts only after an explicit creation request in a normal turn. It is **not** available inside the temporary read-only advisory scope. No `/setup-commit` retrofit, scanner route, Opportunities Run button or specialist registry expansion is involved.

1. **Inspect alternatives and proposed files.** Load the deferred `programmatic_command` tool and call `inspect` with the missing-capability requirement, a safe lowercase/hyphen command name, ordinary Markdown and any helper text. The first result is a bounded catalog review. Select likely candidates through `candidates` for body inspection, then submit the current inventory hash with the reviewed disposition and rationale. A suitable existing prompt returns `reuse`; manual and app-development outcomes are explicit. Suitability is a reviewed claim, not something a matching name or hash proves.
2. **Review the exact proposal.** A creation proposal returns one session handle and the complete preview: destination paths, exact Markdown/helper strings, raw hashes, parsed prompt identity, prior absence, required tools, prerequisite evidence, risks and verification expectations. Normal Markdown must state inputs, outputs, required tools, limits and argument behavior. There is no new frontmatter language or `$ARGUMENTS` substitution.
3. **Ask separately to create.** `create` accepts only that handle. The normal desktop session asks through its existing question card, with exact content and an explicit warning that creation does not run anything or grant tools. Model booleans, copied approval records and free-text substitutes do not approve it. The handle is consumed before awaiting review; rejection, timeout, cancellation, supersession, conversation changes, disposal and restart do not preserve permission. The host rechecks project identity, inventory, prerequisites and bytes after the answer and before publication.
4. **Publish without replacing files.** The sole discoverable file is `.gg/commands/<name>.md`. Helpers live in the private, non-recursive `.gg/commands/.<name>-helpers/` directory. Existing files/helper sets are conflicts even if they appear generated. Complete synced helpers precede a complete non-`.md` temporary sibling; an atomic hard link publishes the Markdown only if its destination is still absent. Unsupported hard links return unavailable—there is no overwrite rename or direct-visible-write fallback. Lock cleanup is confined to a unique operation-owned directory because the shared lock helper can reclaim stale files.
5. **Inspect loading separately from behavior.** Creation reports `created`, `loads`, `behavior: not-tested` and `executionApproved: false` separately, plus a verification handle. The actual shared loader and discovery resolve the new command immediately, without packaging. `verification` rehashes command/frontmatter/helpers/prerequisites and checks owner, selected runtime environment and append-only arguments. Same-session recommendation data names those limits; no universal verified badge is added.
   Verification responses keep `loads` separate from `reviewedContent: current | unavailable`, receipt validity and optional model judgment. `loads: true` means actual discovery resolved the expected project command owner in this inspection; `loads: false` means discovery returned no command for that identity. The field is omitted when loading is unknown (for example, cancelled/unknown session state, owner mismatch or failure before discovery). `reviewedContent: current` requires all reviewed snapshot checks; `unavailable` means that identity was not established, not that Markdown cannot load. Command/frontmatter/helper/prerequisite edits can therefore return `{status: "unavailable", loads: true, reviewedContent: "unavailable", behavior: "unavailable", executionApproved: false}`. Missing, forged, evicted, capped or stale receipts leave a successfully checked snapshot and loader as `{status: "unavailable", loads: true, reviewedContent: "current", behavior: "unavailable", executionApproved: false}` when only receipt validation fails. Rejected evidence returns no report, receipts, recommendation or model judgment; evidence-size rejection also preserves the independent observations. These are session-local observations, not a verified badge or permission to execute.
6. **Prepare evidence without running tests.** `prepare_verification` records the exact foreground bash command, test-file digests and requested assertion cases. It runs nothing and approves no execution. Separately authorized normal file/bash tools may run the target project's reviewed fixture tests. The guarded session lifecycle records up to 64 host-generated test-result receipts, distinct from advisory retrieval receipts. The subsequent `verification` operation accepts only receipt IDs actually observed in this session, never model-authored call IDs as proof.

Inspection limits are one pending proposal, one Markdown plus at most 32 helpers, 128,000 bytes per file, 512,000 private content bytes and a 64,000-byte complete JSON review ceiling. Oversize reviews are rejected, not truncated into approval. Catalog inspection uses existing bounded discovery limits and fails closed on incomplete/unreadable enumeration, including hidden filename/frontmatter/alias/case collisions. Only regular bounded UTF-8 files are accepted; traversal, Windows device/ADS/trailing-dot paths, links and unsafe ancestors are refused. The initial helper runtime is the installed host Node executable (`.js`, `.mjs`, `.cjs` plus text/JSON/Markdown data); other runtimes are explicitly unestablished. Declared installed packages require readable, regular local manifests; linked package directories may be unavailable under this policy. No prerequisite is installed.

Before the Markdown commit point, interrupted work can leave private helpers/staging only. Caught failures remove only still-matching operation-owned files and empty owned directories; changed user content is retained with residual paths. Old crash leftovers are not blindly reclaimed. After the commit point, notification or subsequent-check failure must still report that files were created. These path checks do not provide kernel-level directory-handle confinement against a hostile same-user process replacing ancestors, and fixtures are not an OS sandbox.

Project-bound verification receipts exclude every `bash` call with `persist: true`, even its first call or a platform fallback. Persistent execution still works normally, but its diagnostics describe the launch directory and the host's environment fingerprints do not attest the reused shell's current directory or modified exports. Preparation and verification report this evidence limitation. Use a separately approved nonpersistent foreground call (`persist` omitted or `false`) for a limited receipt. Printed `pwd`/environment output is not trusted provenance; broader support requires a transport-owned cwd/environment attestation contract.

**Evidence limitations are deliberate.** A host-observed process completion, exit code or printed “all tests passed” is not proof that arbitrary requested assertions ran. Receipts bind actual invocation input, command/helper/test bytes, configured provider/model, selected environment, output identity/capping and available host execution diagnostics. Known wrong working directories, edits during a test, later edits, wrong model/environment, duplicated calls, forged IDs, capped output and restarted state invalidate applicable evidence. Declared assertion coverage and optional model judgment stay explicitly labeled. Unlisted dependency source and environment inputs are not fully fingerprinted.

The tool deterministically establishes loading only. Without host-established assertion linkage, the overall behavioral report remains `unavailable`, including for a zero-exit process; it never invents a universal parser or grading platform. Actual normal/incomplete/out-of-scope prompt wiring and executable helper normal/error/unchanged-file assertions are exercised by GG's existing scripted-provider/Vitest/Node fixtures. They do not evaluate arbitrary live-model quality. Real-model or paid trials require separate authorization.

Creation is unavailable without a human-review callback (including ordinary headless/CLI hosts), under denied tool policies, without local filesystem support, or in plan mode. Persistent child workers do not receive this tool automatically. Read-only inspection/evidence operations grant no file or execution permission. Other sessions must re-inspect helper assumptions; advisory script-backed availability remains explicitly unsupported. Updates, overwrites and global promotion remain outside this create-only workflow.
