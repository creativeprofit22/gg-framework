# Programmatic workflow

GG assesses project needs through its existing session/provider engine, independently of how many deterministic scanners are enabled. Discovery and recommendations do not approve saving settings, creating commands or running tasks. Use the focused pages below for the authoritative rules.

| Start here | What it owns |
| --- | --- |
| [User flow](programmatic-user-flow.md) | Setup-first slash commands versus desktop **Discover opportunities**, current controls, review/approval, configuration drift and scanner recovery. |
| [Architecture](programmatic-architecture.md) | Module/interface owners, catalog refresh, native bridge, fixed scanner routes and scanner state. |
| [Evidence](programmatic-evidence.md) | Samples versus delivered receipts versus strict inventory, permissions/budgets, research attribution, external reference ledger and retained developer verification material. |
| [Recommendation policy](programmatic-recommendation-policy.md) | Needs-first five-way decisions, alternatives, repeatability, stock/depot/consent and no-op worked examples. |
| [Recommendation history lifecycle](programmatic-recommendation-lifecycle.md) | History consent, compatibility, identity, decisions, persistence, retention and recovery. |
| [Capability extension](programmatic-capability-extension.md) | Unfamiliar-stack walkthrough, command identity, inspect/create/verify/run separation, no-clobber publication, confinement limits and existing test owners. |
| [Evaluation](programmatic-evaluation.md) | Six synthetic inputs, five-dimension rubric, local check commands and separately approved live-call protocol. |

The [scoped verification record](../.gg/evidence/cross-project-discovery-verification.md) separates local results from outstanding live-model quality and installed-build evidence.
